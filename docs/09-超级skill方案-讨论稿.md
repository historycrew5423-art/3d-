## 〇、两分钟版本

**要解决的事**

两个人加一堆 agent 同时做一个 3D 网页游戏，大量时间花在和“游戏好不好玩”无关的地方：信息不同步、做出两个游戏、合并丢优点、提交打架、不知道上线哪一版、穿模和绑骨、字挡住角色、音效和素材来回传、做过的东西下次重做。

**根因只有三个**

1. 没有唯一的“准”。
2. 容易出错的地方没有固定检查。
3. 做过的东西留在某一条线里，带不到下一个游戏。

**方案一句话**

skill 本身只是一页纸的总入口，负责指路。真正把事做掉的是它后面的三样：几条命令、一个比赛仓库模板、GitHub 上的自动检查。另外有一个跨比赛越攒越厚的手册仓库。

**九个要点**

1. 一个仓库说了算：现状、决定、规矩都在仓库里，所有 agent 读同一份。
2. 开场定“六项不许分叉”。要试两种玩法就限时“赛马”，选一个当底，再用“优点卡”一条一条搬。
3. 所有活从一个“收件口”进主线，GitHub 把关。谁的活都不会被盖，也不会丢。
4. 一条命令上线：自动版本号、每版一个文件夹、线上核对、二维码、一键退回。
5. 素材一条命令入库，自动出检查图。场景按“合同”分两步交。
6. 镜头、界面、声音做进公共底座，新游戏一开始就有。
7. 素材和声音进共用的库，有目录页，不再传压缩包。
8. 经验按“四级台阶”升级：同一个坑出现第二次，就从“记下来”升成“自动检查”或“默认自带”。
9. 平时只用说十来个口令：“开工”“收工”“定了”“反馈”“对表”“上线”等。

**对我们两个人意味着什么**

- 要养成的习惯只有四个：让 agent 从“开工”开始、以“收工”结束；开场一起分地盘；每两小时对表五分钟；真手机试过再转正。
- 不用再做的：传“最终版.zip”、手改版本号、写几十 KB 的交接文件、给每个新 agent 贴开场提示词、同一个模型处理两遍、最后一刻手工缝两个游戏。

**要直说的三件事**

- 底座和素材线最花工夫。而且按上一场的规则，赛前写好的底座多半不能直接带进比赛，只能带规格，开赛后现场重做。
- 自动检查管不了“好不好玩、好不好看、卡不卡”，真手机还得人来试。
- 前提是两个人和所有 agent 都只在一个仓库里干活。有一边还在仓库外面做、靠压缩包往来，信息同步这一块就不起作用。

**先后顺序**

依次是：收拾现场、骨架和入口、上线命令、开赛命令和收件口、素材线、底座、演习、赛前体检。经验卡和提示词的整理和前面几步并行。前四步做完，协作类的问题就基本管住了。

## 名词表

- **手册仓库**：长期保留的那个仓库，放 skill、命令、模板、经验卡、提示词、素材库。暂定名 `hackathon-kit`。
- **比赛仓库**：每场比赛一个，从模板建出来，两个人和所有 agent 只认它。
- **底座**：所有游戏共用的那部分代码：画面、输入、镜头、界面、声音、读模型、加载、调试开关。
- **现状板**：仓库里每人一个小文件，写着在做什么、下一步、等谁拍板。随时覆盖。
- **已定的事**：定下来的决定，只增不改。同一件事，新的取代旧的。
- **一页纸**：由“已定的事”自动生成的一页说明，给人和给 agent 看的都是它。
- **认领**：agent 动手前先在现状板写明做什么、会动哪里，另一边看到就避开。
- **收件口**：活进主线的唯一通道。先交到小分支，GitHub 上的自动检查通过才合进主线。
- **赛马**：两种玩法都想试时，只用方块、限时两三个小时各做一版，到点评比。
- **优点卡**：一条优点一张卡，写明是什么、为什么好、靠哪些文件和数字实现、搬过去怎样算成功。
- **入库**：新模型、新声音进仓库的那条命令，自动处理并登记。
- **试衣间**：入库后自动出的一张检查图，一眼看出模型能不能用。
- **场景合同**：场景必须交代清楚的几件事：地面多高、哪里挡路、从哪出怪、边界在哪。
- **播报台**：游戏里所有的字都交给它排队显示，同一位置一次一条。
- **经验卡、提示词配方、口味档案**：一个坑一张卡；一类提示词一份配方；队长反复提的要求整理成的一页验收标准。
- **收口口令**：对只能聊天的工具说的一句话，让它把聊定的事按固定格式输出，贴回仓库才算数。
- **投递包**：推不上 GitHub 时交活用的文件包，里面记着它是从哪一版改的。
- **发布人**：唯一有权把试玩版转成正式版的人。

## 一、我们现在怎么做，卡在哪

**现在的流程**（队长的描述）

1. GPT 出角色图。
2. Tripo 或 Hi3D 生成 3D 模型，减面、绑骨、加动作。
3. 想游戏方向和玩法，写成一份 Markdown。
4. Midjourney 出场景图，交给大模型用 three.js 搭场景。同时把仓库链接当提示词，让 agent 带着以前的经验做。
5. 一轮一轮试玩、调整、找 bug。
6. 做成公开链接，WorkBuddy 做成扫码直接玩。

**卡住的地方**

- **协作类**：两人同时开工，之后要合并；GPT、Claude、Kiro、WorkBuddy 来回用，信息不同步，两个人之间更不同步；经常做出两个游戏，合并时吸收了缺点、丢了优点；不知道上线哪一版；每次上线重走一遍老路。
- **制作类**：角色穿模；绑骨出问题；没有多视角切换；提示画面太多；角色被字挡住；音效没收集好、不同步；互拿数据浪费时间。
- **积累类**：技术不复用；对话的迭代记录、提示词没有积累。

**记录里反复出现、但没被提到的**

- 几乎每份交接说明都写着“没在真手机上测”。手机上出现过：微信里两边黑边、没声音、国内不翻墙打不开。
- 版本号靠手改，手机拿到一半新一半旧的文件就白屏。
- 线上是哪一版、在哪个地址，没有一处记着。README 里的游乐场链接指向 `/arcade/`，打开是 404，实际地址是 [`/games/`](https://historycrew5423-art.github.io/hackathon-3d-game/games/)。
- 设计改了，给队友和其他 agent 的提示词还是旧的。
- 密钥只存在某一个沙盒里，换 agent 就得重新授权。
- 梗音效和角色形象的授权没核实。
- Kiro 建不了仓库、开不了 Pages，必须有人提前点好。
- agent 要么干等确认，要么不等确认蒙头干。
- 从提交记录上认不出是谁做的：几乎所有提交署的都是同一个名字。

## 二、三个根因

**1. 没有唯一的“准”**

- 现状、决定、版本散在聊天、压缩包和文件夹拷贝里。
- `nai` 里并存三条线：[主线](https://historycrew5423-art.github.io/nai/)、[`classic/`](https://historycrew5423-art.github.io/nai/classic/)、[`naiwa/`](https://historycrew5423-art.github.io/nai/naiwa/)。
- `hackathon-3d-game` 里奶蛙梦境有四个目录：`naiwa_dream`、`hi3d-frog-dreams-web`、`hi3d-handoff`、`naiwa-remake`。
- 10 月 31 日 17:05 到 17:32，“抽象版”换了三种定义，见 [`nai` 交接文件](https://github.com/historycrew5423-art/nai/blob/dev/HANDOFF.md)开头几条。

**2. 容易出错的地方没有固定检查**

- 模型进游戏、合并、上线之前都没有关卡。穿模、绑骨变形、字挡角色，都是玩到了才发现。
- 查过 7 个仓库的所有分支：自动检查一个都没有；能被工具自动读到的规矩，只有 `kiro-chat-archive` 里[一份 Kiro 规则](https://github.com/historycrew5423-art/kiro-chat-archive/blob/main/.kiro/steering/archive-sync.md)。

- 三种视角切换、声音分层、梗的节奏，10 月 31 日的缝合版都做出来了（[缝合说明](https://github.com/historycrew5423-art/nai/blob/dev/naiwa/缝合说明.md)），却仍然在问题清单上。

## 三、方案总览

**四层**

- **总入口**：一页纸的 skill。告诉 agent 先读什么、现在是哪个阶段、该读哪一页、该跑哪条命令。
- **命令**：开工、收工、入库、上线、复盘这些，一条命令做完一整件事。
- **比赛仓库模板**：每场比赛从它建仓库，现状板、已定的事、入口文件、自动检查都是现成的。
- **GitHub 上的自动检查**：守着主线，不通过就不让进。

**规矩分软硬两层**

- 软的写在 skill 里，靠 agent 照做。
- 硬的放在 GitHub 上，哪个工具没读 skill 也绕不过去。

**每一块治什么**

- 一个仓库说了算（4.1）：信息不同步、互拿数据。
- 六项不许分叉、赛马、优点卡（4.2）：做出两个游戏、合并丢优点。
- 并行施工规则（4.3）：提交打架、活被盖掉、活丢了。
- 一条命令上线（4.4）：不知道上线哪版、每次重走老路。
- 素材线和场景合同（5.1）：穿模、绑骨、同一个模型处理两遍。
- 底座里的镜头、界面、声音（5.2）：没有多视角、字挡角色、没声音。
- 经验四级台阶（5.3）：技术不复用、提示词不积累。

## 四、协作篇

### 4.1 信息同步：一个仓库说了算

**会怎么出问题**

- 在 GPT 或 Claude 里聊定的事、两个人口头说定的事，其他 agent 不知道。
- 人成了传话筒：在 agent 之间手动复制粘贴，转述一次走样一次。
- 文档越积越多，分不清哪份现行。`nai` 里有 18 份文档加一份 53KB 的[交接文件](https://github.com/historycrew5423-art/nai/blob/dev/HANDOFF.md)，其中好几份已经整份或部分作废。
- 新 agent 开工前要读的东西太多，读完还是会漏。
- 任务派错了 agent：让沙盒里的 agent 去看抖音视频，来回好几轮没看成。
- 聊天里发的图，别的 agent 拿不到。
- 密钥只在某一个沙盒里。
- 两个人之间没对表，各自带着 agent 往前跑。

**解法**

- **只认一个仓库**：每场比赛只有一个比赛仓库，两个人和所有 agent 只认它。
- **信息分三层，各有固定位置**：
  - 已定的事：只增不改，同一件事新的取代旧的。
  - 现状板：每人一栏，随时覆盖。
  - 过程记录：每次会话一条小结，只追加，平时不用读。
  - agent 每次必读的只有前两层，合起来不超过两页。
- **一页纸自动生成**：由“已定的事”生成。给队友和其他 agent 的提示词只引用它，不再各抄一份，也就不会过期。
- **作废有标记**：一件事被新决定取代时，命令自动给旧文档盖上“已作废”。
- **规矩只写一份**：各工具放一个只有几行的指路文件指向它，见第六节。
- **收口口令**：进不了仓库的聊天模型，聊完让它按固定格式输出一张“决定卡”，贴回仓库才算数。口头说定的事同样处理。
- **分工表**：哪类活派给哪个 agent，哪些只能人做（授权、真机试玩、提供视频截图）。
- **交接五行**：中途换 agent，旧的写清做到哪、哪些改了一半、怎么验证、下一步、有什么坑；新的先用三句话复述，再动手。
- **参考图进仓库**：聊天里用到的图和视频截图存进固定目录，之后只按路径引用。
- **钥匙清单**：只记有哪些钥匙、在哪台机器、怎么重新授权，不记内容。钥匙写进公开仓库，额度会被别人用掉。
- **两个人每两小时对表五分钟**：一起看一眼现状板。

### 4.2 不做出两个游戏

文件不打架，不等于做出来的是一个游戏。这是另一层问题。

**为什么会做出两个**

- 两个人各自对 agent 描述同一个想法，agent 各自补全细节，补出来就是两个游戏。
- 设计方案没有进“准”。11 月 8 日的《奶蛙：笑到最后》方案是两个合并请求（[#1](https://github.com/historycrew5423-art/hackathon-3d-game/pull/1)、[#2](https://github.com/historycrew5423-art/hackathon-3d-game/pull/2)），到现在还开着没合并，两条线各做各的。
- 试两种玩法本身没错，错在没约定什么时候二选一，于是一直分到截止。

**为什么合并会丢优点、收缺点**

- 优点没写下来。合并的 agent 只看得到代码，看不到“哪里好玩”。
- 优点往往是一整套：代码、调好的数字、素材、声音。“梗的节奏”是在队长反馈“搞笑音效太密”之后才调出来的一套数字；只搬梗音效不搬这套数字，问题就原样回来。
- 两套都留，游戏变重变复杂，评委 10 秒看不懂。
- 合并总发生在截止前，没时间试。

**解法**

- **六项不许分叉**：一句话玩法、镜头和操作、主角是谁、一局怎么算完、美术基调、技术底座。开场写在一页纸上并合进主线。这六项不一样，就是两个游戏。
- **要试两种玩法就明着“赛马”**：只用方块做核心玩法，限时两三个小时，到点评比。方块阶段赛马只花两三个小时，做完美术再赛马要花掉整场比赛。
- **评比用固定的卡**：10 秒能不能看懂、想不想再玩一局、手机上顺不顺、离做完还差多少。两个人都用手机各玩两分钟，最好再拉一个外人。
- **选一个当底，另一个只当“捐赠者”**：打上标签、留一个链接供对照，不再往下做。
- **优点卡**：每条优点一张卡，写明是什么、为什么好、10 秒录屏、靠哪些文件数字和素材实现、搬过去怎样算成功。缺点也写卡，写明不要带过来。
- **一次搬一张卡**：搬完把原版和新版两个链接并排玩，按卡上的标准验收，不合格就整条撤回。这样每搬一条，游戏只会变好或者不变。
- **请一个没参与任何一边的新 agent** 写对比报告、起草优点卡，避免两边的 agent 各说各的好。
- **两个都舍不得**：做成同一个游戏里的两关，前提是六项一致。每人一个关卡目录，用网址参数切换。
- **只交换源码**：不交换打包后的文件。重制版就是在打包后的文件上拆开来改的。
- **自动提醒**：现状板一旦发现第二个能玩的版本，就标红。

### 4.3 两边的 agent 同时干活不打架

**11 月 8 日就是一次完整的“打架”**

- 同一天、同一个仓库里跑着两条线。一条在分支上：四个绑骨角色、白虎岭割草模式、视角切换。另一条直接推主线：奶蛙梦游记、打包版、重制版。
- 北京时间 14:14，主线上出现一次“两处同时推送”造成的合并。14:21，分支那条也把主线合进来了一次。
- 最后上线的是主线那条。分支那条的活至今停在 [`feat/naiwa-meme`](https://github.com/historycrew5423-art/hackathon-3d-game/tree/feat/naiwa-meme)（领先主线 4 个提交）和 [`assets/rigged-characters`](https://github.com/historycrew5423-art/hackathon-3d-game/tree/assets/rigged-characters)（领先 2 个），没进主线，线上也没有。
- 队友的账号 [diexiewang-del](https://github.com/diexiewang-del) 那天往主线推了 9 次，10 月 31 日往 `nai` 的 `dev` 推了 3 次（缝合版的三版）。这些提交署的全是队长的名字，所以从记录上分不清哪一步是谁、哪个 agent 做的。

**“打架”其实有十种**

1. **撞车**：两边改了同一个文件的同一处。
2. **覆盖**：一边用旧版本整文件、整文件夹地盖掉另一边的新改动，包括强制推送和解压缩包覆盖。最伤，而且不报错。
3. **暗伤**：合并没报冲突，合起来却跑不了。比如一边改了公共的东西，另一边还按旧的用。
4. **搁浅**：活做完了停在分支上，没人合。割草模式就是。
5. **抢上线**：两边先后发布，后发的盖掉先发的；或者从没同步的本地发布，线上对不上任何一版。
6. **重复劳动**：两边的 agent 做了同一件事，或者各生成了一遍同一个角色。
7. **越界**：agent 顺手整理、改名、重排别人的文件。Windows 和 Mac 换行符不同，也会让整个文件显示成“全改了”。
8. **自动生成的文件打架**：打包文件、版本号这类每次都变的东西，谁动谁冲突。现在每次改动都要把所有文件里的版本号替换一遍，等于每次都碰所有文件。
9. **丢活**：沙盒重置、账号断线、推送失败没发现，活只存在某个 agent 那里。
10. **认不出是谁**：所有提交署同一个名字，出了问题不知道找哪边。

**解法：并行施工规则**

先让撞车在结构上变少：

- **分地盘**：每人一个关卡目录，只动自己的。
- **一样东西一个文件**：每个素材、每次会话记录、每人的现状各占一个小文件，总表由命令自动拼出来，没有需要两边同时改的“大名单”。
- **自动生成的东西不进主线**：打包文件和版本号只在上线时生成。
- **底座是公共区**：比赛期间只加不改不删。要改得先在“已定的事”里落一条。
- **跨系统统一**：换行符、文件名大小写、文件名只用英文和数字。

动手前先认领：

- agent 开工的第一个动作，是在现状板自己那栏写清做什么、会动哪里，并先把这一条推上去。
- 另一边的 agent 每次同步都会看到，避开或者排队。
- 认领两小时没动静自动作废。

所有活都从一个“收件口”进主线：

- 谁都不能直接推主线，也不能强制推送。这是 GitHub 上的设置，不靠 agent 自觉。
- agent 每完成一小步就把活交到自己的小分支，最长不超过半小时交一次。
- GitHub 上的自动检查通过才合进主线：有没有越界、能不能跑、自动试玩一分钟有没有报错。没过就不合，并写明原因。
- Kiro 本来就是推分支再开合并请求，这套流程和它的习惯一致。

撞了按固定办法处理：

- 不许“整个文件用我的”，不许删对方的文件。
- 冲突在别人地盘或公共区：保留对方的，把自己的改动重新加上去。
- 十分钟解不开：把活停到一个停车分支并推上去，自己回到主线干别的，在现状板标“等人拍板”。

活丢不了、看得见：

- 每次交活先推上云，哪怕没通过检查。
- 每次提交由命令写明是谁、哪个 agent，不管当时登录的是哪个账号。
- 现状板显示：谁的 agent 在做什么、多久没交了、哪些分支的活还没进主线。割草模式那种搁浅，当天就能看到。

上线不抢：

- 只能从主线上的某一版发布，本地没同步就拒绝发布。
- 每一版发到自己的文件夹，互不覆盖。只有发布人能转正。

**“一边的 agent 还在跑，另一边的先跑完”会怎么走**

把两个人叫甲和乙。甲的 agent 还在跑，乙的先跑完：

1. 乙的 agent 交活，检查通过，进主线。甲的 agent 不受打扰。
2. 甲的 agent 交活时，命令先把甲的改动接到最新主线后面。
3. 地盘不重叠是正常情况，直接通过。
4. 如果乙动了甲用到的公共部分，自动试玩会失败。甲的 agent 会收到“你开工之后主线变了什么”的清单，自己改到能跑再交。
5. 两边同时交：一个一个过，后到的自动接在先到的后面重新检查。

任何情况下，乙的活不会被盖，甲的活不会丢。甲乙对调也一样。

**需要人做的只剩三件**

- 开场分好地盘。
- 玩法层面的分歧拍板。
- 发布人负责转正。

### 4.4 上线

**会怎么出问题**

- 不知道线上是哪一版。压缩包叫“最终版”“以这一版为准”，网址有好几个。
- 手机缓存：一半新一半旧就白屏，微信里更顽固。
- 每个托管平台走法不一样：Pages 换过发布分支，WorkBuddy 要交文件包（[部署说明](https://github.com/historycrew5423-art/nai/blob/dev/naiwa/部署说明_给WorkBuddy.md)），还有一条要手动同步的 `site` 分支。
- 发上去才发现坏了：文件名大小写不对、用了绝对路径、文件太大、模型只传了占位文件。
- 国内不翻墙打不开；有的手机不支持所用的画面技术。
- 没法快速退回上一版。
- 现场网络出问题没有备份。
- 把试玩链接当正式链接发了出去。

**解法**

- **版本号自动生成并显示在游戏角落**，截图和反馈都带着它。
- **每一版一个文件夹**，发上去就不再改。正式链接只是“指向哪一版”，二维码永远指正式链接，退回就是指回上一版。
- **上线命令做四步**：
  1. 检查：用到的文件都在不在、文件名大小写对不对、有没有绝对路径、有没有超大文件、有没有把钥匙带上去。就是那份 WorkBuddy 部署说明里手写的那些项。
  2. 发到清单里的每个平台。
  3. 逐个打开，核对版本号和有没有报错。
  4. 把结果写回现状板。
- **每次进主线都自动发一个试玩版**，到最终发布时这条路已经走过很多遍。开赛第一个小时先发一版上线，哪怕只是一个空页面，证明这条路通。
- **试玩版带水印**，不会被当成正式版。
- **真机闸门**：转正前必须有人登记，在至少两台真手机上看到了这个版本号，其中一台在微信里打开、一台不开代理。
- **最后一小时只修会卡死的问题**，并保留一键退回。
- **演示备份**：上线命令顺带产出一份离线包，并提醒录一段 30 秒视频。
- WorkBuddy 的发布机制还没实测：换版本后网址变不变、能不能自动发，要试过才能定。

## 五、制作篇

翻仓库看到的一个事实：这一篇里的大部分问题，都至少解决过一次，但解法留在了当时那个游戏里，下一个游戏、另一条线又从头来。所以这部分主要是把做对过的东西固定下来，要新发明的不多。

### 5.1 素材和场景

**会怎么出问题**

- **模型太重**：没设面数上限的 Tripo 模型每个约 190 万面、70MB，Hi3D 的约 500 万面。Blender 直接打开会内存崩溃，普通减面会把贴图撕成迷彩。
- **同一批模型处理了两遍**：西游那四只小怪，一条线减到约 3.2 万面，另一条线换了办法做到约 7000 面，两边起的名字也没完全对上。四个原始文件共约 287MB 还放在 [`assets/models/`](https://github.com/historycrew5423-art/hackathon-3d-game/tree/main/assets/models) 里，仓库已经约 1.3GB。
- **规矩每次重定**：Hi3D 的模型脸朝一个方向，Tripo 的朝另一个，[场景建构提示词](https://github.com/historycrew5423-art/hackathon-3d-game/blob/main/hi3d-handoff/reference/奶蛙七十二变_三重梦境_3D场景建构提示词-mw7alrp7-9ded7702.md)又规定了第三个。一边做的东西拿到另一边，要重新对方向、大小、脚底。
- **绑骨**：手臂下垂的容易绑错，大婚纱挡住腿绑不了，披风和盔甲一动就变形。
- **场景做成了“画”，游戏要的是“关卡”**：白虎岭自己带着一套画面和运行程序，不能直接放进游戏；金圈周围的地面往北低约 7 米、往南高约 19 米；贴图要占手机约 305MB 的显示内存（[交接说明第五节](https://github.com/historycrew5423-art/hackathon-3d-game/blob/main/naiwa_dream/交接说明.md)）。
- **穿模是五种不同的问题**：
  - 人穿过墙和树：场景只有样子，没有“哪里挡路”。
  - 人陷进地里或飘着：地面不平，或脚底没对齐。
  - 怪叠在人身上。
  - 镜头钻进墙。
  - 衣服穿过身体：这一种属于绑骨。

**解法**

- **先列需求再做重活**：角色长什么样可以先定，但减面、绑骨、做动作要等需求单。需求单从那一页玩法里列：每个角色同屏几只、离镜头多远、要哪些动作。这段时间玩法先用方块跑着，素材做好一个换一个。
- **规格只定一次**：一个单位多长、脸朝哪、脚底在哪、挡路的隐形方块和出怪点怎么命名、每类素材的体积上限、统一的画风前缀。所有出图、建模、搭场景的提示词都引用这一份。
- **在最前面一步解决**：出图时就要求 T 字姿势、双腿分开、披风到腰、手里不拿东西（[出图和动作](https://github.com/historycrew5423-art/nai/blob/dev/docs/出图和动作.md)里写过这条提示词）；Tripo 生成时就设面数上限。10 月 31 日那六只怪设了上限，每只约 2800 面，是那四只的几百分之一。
- **入库命令和试衣间**：
  - 按用途选配方（主角、Boss、成群小怪、道具），自动减面、缩贴图、统一大小朝向和脚底。
  - 登记来源、提示词、花费、授权。提交比赛时要勾的工具清单也从这里生成。
  - 自动出一张检查图：四个方向、旁边一个 1.8 米的标尺人、每个动作几帧、手机上的实际大小。脚底、大小、体积由命令判，其余人看 10 秒。
- **绑骨有固定答案**：
  - 成群的小怪：不绑，用代码做蹦跳摇晃。
  - 人形、看得见腿、手臂张开的主角和 Boss：用 Tripo 自动绑骨加预设动作。
  - 大裙子、长披风、非人形：不绑，或者回到出图那一步改短重做。
- **场景合同，分两步交**：
  - 第一步只交“白模关卡”，写清地面多高、哪里挡路、从哪出怪、边界在哪，放进底座用方块就能玩。
  - 第二步照参考图上美术，不许动第一步的布局。
  - 合同每一条都配自动检查，其中一项是让角色自动把场景走一遍，记下陷地、穿墙、卡住的位置。那份场景提示词的验收条件里写过“没有穿模”，但没有东西去查它。
- **素材库**：
  - 成品放进两个人共用的库，有缩略图目录，按文件内容自动认出重复。
  - 原始大文件不进比赛仓库，放 GitHub 的“发布”（Releases）附件，库里记链接。
  - 每个素材带着能重做它的提示词和参数，比赛不许带成品时照配方重做也快。

### 5.2 镜头、界面、声音

**会怎么出问题**

- **镜头每次重做**：三种视角 10 月 31 日的缝合版就有。11 月 8 日搁浅的 `feat/naiwa-meme` 分支，提交说明里又出现了“视角切换”和“视角按钮”。难在连带的东西：操作方向、怪从哪出来、血条朝哪、场景背面好不好看、镜头会不会进墙。只加一个切换按钮，这些都会坏。
- **字越加越多**：喊话气泡、两行字幕、头顶冒字、横幅、血条、连杀大字、目标、倒计时、选卡，各放各的，没人管整块屏幕。弹窗也多，10 月 31 日队长的反馈里有“一下子放一堆对话”。
- **agent 自查时不容易看见字**：它截图用的浏览器没有中文字体，字是方框，[经验文档](https://github.com/historycrew5423-art/kiro-chat-archive/blob/main/knowledge/threejs-scene-workflow.md)里记的做法是截图前把字藏起来。`nai` 那次专门按手机尺寸走了一遍界面，就查出了按钮压住倒计时。
- **声音到处是副本，共享包只进不回**：
  - `hackathon-3d-game` 主线上有 156 个声音文件，内容不同的只有 67 个。17 个梗音效各存了 6 份、用了 3 种文件名。
  - [`assets/audio/`](https://github.com/historycrew5423-art/hackathon-3d-game/tree/main/assets/audio) 那个共享包建好之后，新加的 38 个（喷嚏、掌声、全部配音）只留在 `naiwa_dream` 里。
- **授权口径没定过**：hi3d 那版起初写明不用来源未核实的梗音频（[复用说明](https://github.com/historycrew5423-art/hackathon-3d-game/blob/main/hi3d-handoff/source/hi3d-reuse-notes.md)），第三轮按要求又加了回来。

**解法**

- **镜头做成底座的零件**：
  - 连带的东西一起包进去。
  - 开场定一个主视角，其余算加分；每一关声明支持哪几种，跑酷固定在背后，现在已经这样做。
  - 验收时每种视角各截一组图，再加玩家能拉到的最极端角度。11 月 5 日只截了开场和平视，结果镜头一拉到山顶往下看，背光面全黑、楼是盒子。
- **屏幕分区**：主角周围一圈是禁区，常驻的字和按钮不许进；四个角和底部一行是固定位置。
- **所有字走一个“播报台”**：
  - 功能只说“想显示什么、多重要”，由播报台排队，同一位置一次一条，到时间就撤。
  - 声音已经有同样的规则（同时只叫一只，重要的才能顶掉），照搬到字上。
  - 教学提示只出现一次，能演示就不写字。缝合版开局第 8.5 秒自动放一次大招，就是好例子。
- **自动试玩量三个数**：主角被字盖住多久、同时出现几条字、第一分钟被弹窗占掉多少秒，超了不通过。测试环境装上中文字体，验收截图不许藏字，横屏、竖屏、微信里的窄屏各截一遍。
- **声音库和试听页**：
  - 一个网址，点了就能听，有标签、时长、授权颜色（绿可公开，黄只限比赛演示，红别用）。
  - 入库时裁掉不用的部分，统一音量和命名。“闪身步”那条 14 秒，只用了开头 0.72 秒。
  - 收工时新加的声音自动回到库里。
  - 授权底线开场定一次，写进“已定的事”。
- **底座自带基础声音**：打中、受伤、升级、按钮、胜利、失败用授权干净的通用包，第一个小时就有声音。主角、小怪、效果三条线，梗的节奏，手机静音键的处理，也都放进底座。
- **游戏里只写事件名**：哪个事件放哪个声音、多大声、隔多久能再放，写在一张表里。换声音不改游戏代码，队友可以单独管这张表。自动试玩顺带报告哪个事件没配声音、哪个声音从没响过。

### 5.3 经验、对话、提示词

**会怎么出问题**

- 记下的东西其实很多：`kiro-chat-archive`、`3d-`，还有 `nai` 里 55KB 的[开发日志](https://github.com/historycrew5423-art/nai/blob/dev/docs/开发日志.md)和 53KB 的交接文件。问题出在“用”上。
- **记下了但还要靠人记得，就会再犯**：
  - 版本号的事 10 月 31 日就记了“以后每次改都要换”，11 月 8 日 `naiwa_dream` 的交接说明里仍是手动全局替换。同一天的重制版做成了自动的，但只留在那一版里。
  - “真手机没测”在 11 月的四份说明里各写了一次。
- **流水账新 agent 用不上**：按时间写的记录读不完，读了也分不出哪条和手头的活有关。把仓库链接当提示词，它读了多少、有没有读到点上，没法保证。
- **提示词和结果对不上**：`nai` 的[生成记录](https://github.com/historycrew5423-art/nai/blob/dev/assets/ref/生成记录.md)记了每张图的提示词和花费，这个做法好。但哪条出的图最后用上了、哪条作废了，要翻文档才知道。Midjourney 的场景图，在仓库里没搜到提示词记录。
- **固定规矩和当场内容混在一份提示词里**：那份 17KB 的场景建构提示词，命名规则、验收条件这些每场都一样的，和剧情、笑点写在一起，下一场只能整份重写。
- **试玩反馈最值钱，却埋在流水账里**：没音效、角色没动作像贴图、手机不全屏、文字像硬打的。换一个游戏、换一个 agent，它不知道这些标准，只能等队长再说一遍。

**解法**

- **一条经验有四级台阶**：
  - 经验卡：读到才有用。
  - 清单：到点必须打勾。
  - 自动检查：不过关就拦住。
  - 底座默认：谁都不用记。
  - 同一个坑出现第二次就升一级。按这条规则，版本号直接升到最高一级，真机测试升到自动检查，4.4 里的上线命令和真机闸门就是这么来的。
- **经验卡**：一张卡一个坑，写现象、原因、解法、怎么查、适用的工具版本。skill 在每个阶段只把相关的几张交给 agent，不让它读整个仓库。`kiro-chat-archive` 里那份 [three.js 场景经验](https://github.com/historycrew5423-art/kiro-chat-archive/blob/main/knowledge/threejs-scene-workflow.md)已经是这个写法，拆开就有二十来张。
- **提示词配方**：
  - 内容：用途、留了空格待填的模板、工具和版本、一张成功的样图、已知毛病和补丁句（比如“不是青蛙”那句）、花费。
  - 每场都一样的规矩只写一次，每场不同的内容来自那一页纸，开工时自动拼起来。
  - 素材入库时必须填提示词；素材进了游戏，这条提示词自动记一次“成功”；作废的留着并写明原因。
- **口味档案和反馈表**：每条试玩反馈记一行，带版本号、原话、处理结果，一次提十几条也不会漏。反复出现的要求整理成一页验收标准，每个 agent 开工必读，第一版就更接近想要的。
- **对话不追求存全文**：Kiro 的自动归档照旧。其他工具只收三样：决定、反馈、好用的提示词，用收口口令。
- **赛后复盘命令**：
  - agent 读这一场的提交记录、小结、反馈表、素材登记，列出候选经验卡、成功的提示词、又出现的老问题、每条该升到哪一级。
  - 两个人花 30 分钟点头或划掉。
  - 同时记几个数，比如开赛到第一个能玩的网址用了多久、合并花了多久。下一场对比，没用的规则删掉。
- **赛前体检**：经验卡写明适用版本。three.js、Tripo、出图模型都在变，赛前一周用当时的最新版本把底座和流水线从头走一遍，过期的卡更新掉。

## 六、这个 skill 长什么样

**现在是怎么接入的**

- 靠一份交接文件加一段复制粘贴的开场提示词。`nai` 的交接文件有 53KB，更新到第 63 轮，规矩、现状、Kiro 沙盒的路径、给队友的话都在里面。
- 它规定每一轮回复之前都要存对话原文、更新日志、更新交接文件、推送并核对。

**由三样东西组成**

- **手册仓库**（长期，只有一个）：skill、命令、比赛仓库模板、底座零件、经验卡、提示词配方、口味档案、素材库。
- **比赛仓库**（每场一个）：说“开赛”，从模板建出来，里面带一份手册的拷贝。任何 agent 拿到这一个仓库就拿到了全部规矩和命令，不用另外装东西，也不靠现场网络。带不带底座，按这场的规则定，见第九节。
- **入口**（每个工具几行）：各工具自动读的文件不一样，Kiro 读 `.kiro/steering/`，Codex 和 Cursor 读 `AGENTS.md`，Claude Code 读 `CLAUDE.md`。每个都放一份，内容只有一句：去读 skill 的总入口。规矩只写一份。

```text
hackathon-kit/        手册仓库
  skill/SKILL.md      总入口，一页：口令表、先读什么、现在该读哪一页
  skill/phases/       每个阶段一页：开赛、玩法、素材、场景、交活、试玩、上线、提交、复盘、交接
  kit/                命令
  template/           比赛仓库模板：入口文件、现状板、已定的事、自动检查
  shell/              底座零件：镜头、界面、声音、输入、加载
  cards/ prompts/ taste.md   经验卡、提示词配方、口味档案
  library/            素材库和声音库
```

- 每个阶段页长得一样：开始前要有什么、步骤（每步对应一条命令）、必须过的检查、要交出什么、相关的经验卡。
- agent 每次要读的：入口几行、总入口一页、现状板和已定的事两页以内、当前阶段一页、相关的几张卡。

**工具分三类接入**

- **能进仓库、能跑命令的**（Cursor、Codex、Claude Code、Kiro，WorkBuddy 按那份部署说明也算）：克隆仓库就自动读到入口。Kiro 的沙盒会重置，入口和 skill 都在仓库里，重新克隆就回来。WorkBuddy 自动读哪个文件还不确定，建的时候实测，读不到就用一句开场白。
- **只能聊天的**（网页版 GPT、Claude）：用命令生成一段开场白贴过去，内容是一页纸加当前问题。聊完用收口口令让它输出决定卡，贴回仓库。
- **推不上去的**：用“投递包”，包里记着它是从哪一版改的，收包后变成一条任务分支，照样过收件口。以后不再传“最终版.zip”。

**每台机器先“体检”一次**

它会说这台机器能干哪些活、缺什么。现有脚本里写死过 Windows 的 Edge 路径和 Kiro 沙盒的路径，换台机器就跑不了。按记录，分工大致是：

- 队长 Mac 上的 Cursor：能建仓库、开 Pages、设保护，有 Blender。适合开赛、素材入库、截图验收。
- Kiro：建不了仓库、开不了 Pages，画面是模拟的，每秒约 1 帧（[Kiro 沙盒限制](https://github.com/historycrew5423-art/kiro-chat-archive/blob/main/knowledge/kiro-sandbox-notes.md)）。适合写代码和文档，不适合判断卡不卡。
- WorkBuddy：国内能打开的网址和二维码。
- 网页版 GPT、Claude：想点子、出图、写提示词。

**我们说的口令**

- 每天用的五个：
  - “开工”：同步、读现状、认领任务，用三句话复述“现在什么情况、我打算做什么”，等人点头。
  - “收工”：交活、写五行小结、更新现状板、放开认领。
  - “定了：……”：记一条决定，重新生成一页纸，给被取代的旧文档盖“已作废”。
  - “反馈：……”：记一条试玩反馈，自动带上当前版本号。
  - “对表”：谁在做什么、线上是哪一版、离下一个时间点还有多久。
- 偶尔用的：“入库”“比一比”“上线”“转正”“退回”“交接”。
- 每场一次的：“体检”“开赛”“提交”“复盘”。
- 忘了说也不要紧：入口文件要求 agent 一开始就做“开工”那几步。活是每半小时交一次的，会话突然断掉最多丢半小时。

**时间也归它管**

- 开赛时填截止时间，它倒推出几个时间点：第一个小时有网址、方块版能玩、素材截止、停止加功能、录备用视频、先交草稿。其中大部分，10 月的[时间表](https://github.com/historycrew5423-art/3d-/blob/main/docs/05-时间表.md)里就写过。
- 每次“开工”和“对表”都报现在该在哪一步、落后多少。
- 过了“停止加功能”的点，“上线”只放修问题的改动。要加新东西得明说“破例”，而且先上到旁边的试玩版。
- 10 月 31 日计划 15:00 停，实际 16:45 还在上新功能，17:05 到 17:32 “抽象版”的定义改了三次。

**和现在比，省掉的**

- 53KB 的交接文件：固定规矩在手册里只写一次，现状板只留当前状态，决定只追加。
- 每一轮都存原文、改三份文件再回复：平时只在有决定或反馈时记一行，收工时写小结。评委要看的制作过程，由小结、决定、反馈和提交记录自动拼成一页。
- 复制粘贴开场提示词。
- 提交时手工列“用过的工具和模型”：从每次提交的署名和素材登记里自动列出。

**手册怎么更新**

比赛中不动比赛仓库里那份拷贝。赛后“复盘”把新经验、新提示词、新素材回流到手册仓库。

## 七、比赛当天是什么样

1. **赛前一周**：赛前体检。用当时最新的工具版本把底座和流水线走一遍。
2. **赛前一天**：两台电脑各跑一次体检，确认账号、额度、密钥都通，都能推送和上线。
3. **开赛后半小时内**：说“开赛”，建好比赛仓库。两人对齐一页纸（六项不许分叉），分地盘，定授权底线，登记这场规则允许带什么。
4. **第一个小时内**：第一版上线，哪怕只是一个空页面。二维码出来。
5. **前两三个小时**：玩法用方块跑起来。要试两种玩法就赛马。同时列素材需求单，开始出图和生成模型。
6. **中段**：各做各的关卡。agent 每半小时交一次活，每次进主线自动发试玩版。素材做好一个入库一个、换一个。每两小时对表五分钟，用真手机试玩一次。
7. **截止前三小时**：停止加功能，只修问题。
8. **截止前两小时**：录备用视频，出离线包。
9. **截止前一小时**：只修会卡死的问题。转正，在两台真手机上核对版本号，先交草稿。
10. **赛后 48 小时内**：复盘，收经验和提示词。

## 八、先做哪些，后做哪些

排序有三条原则：

- 每一步做完就能单独用。
- 每一步都拿现有的游戏当试验品。
- 经验和工具哪场比赛都能带，放前面；底座能不能带要看规则，放最后。

步骤：

0. **收拾现场**（小）
   - 队长 Mac 上的提交署名：没设过名字，提交会自动带上这台电脑的系统账户名，里面有像密码的字样。公开仓库里已有一条这样的提交（[d854f46](https://github.com/historycrew5423-art/hackathon-3d-game/commit/d854f46)）。
   - 搁浅的分支和两个没合的合并请求，逐个定去留。
   - README 里的失效链接。
1. **骨架和入口**（小）：手册仓库、总入口、口令、现状板、已定的事、各工具的入口、开场白和收口口令、赛程时间点。验收：同一句“开工”，我们用的每个工具答出同样的现状。
2. **上线命令**（小到中）：版本号、每版一个文件夹、检查、发布、线上核对、二维码、退回。拿 `naiwa_dream` 试：发两版、退一次、两台手机扫码。顺带实测 WorkBuddy 那条路。
3. **开赛命令和收件口**（中）：一条命令建好比赛仓库，带主线保护、自动检查、Pages、队友邀请。验收是一次“打架演习”：两个 agent 同时改，一个先交，看有没有丢活、冲突有没有按规矩停靠。
4. **素材入库、试衣间、素材库和声音库**（中）：拿那四个 70MB 的原始模型和现有的 67 个声音当第一批，入库结果和手工处理的版本比。
5. **底座**（大，分片做）：依次是声音事件表和基础包、播报台和屏幕分区、镜头、场景合同和巡场、自动试玩。从做得最好的现成实现里提，不从零写。拿一个现有关卡移上去验收。每个零件都配一份规格和重做用的提示词，规则不许带代码时，照着现场重做。
6. **经验卡、提示词配方、口味档案**（小，和前面几步并行）：从现有四个仓库里拆。
7. **演习**（半天）：两个人加各自的 agent，从“开赛”做到上线一个小游戏，再跑一次“复盘”。哪里卡就改哪里。
8. **赛前体检**：比赛前一周。

补充：

- **如果比赛比预想来得早**：做完 1、2、3 和 6，信息不同步、提交打架、上线这三类问题就基本管住了。4 其次，5 可以整块不做。
- **谁来做**：主要由 AI 在队长的 Mac 上建，那里登录的权限够建仓库和开 Pages。每做完一步，需要队长用 Kiro 和手机各试一次，队友用他的工具试一次。
- **先定下的默认值**：手册仓库叫 `hackathon-kit`；发布人是队长；命令用 Node 写，Mac、Windows、云端沙盒都能跑；比赛仓库自带手册拷贝。不合适随时改。
- **队长已经定的**：这套东西不用管隐私。链接、账号名这些照实写、公开放，不做遮挡。钥匙例外，原因见 4.1。

## 九、代价、前提和边界

- **前提**：两个人和各自的 agent 都只在比赛仓库里干活，都走收件口。现在两个人已经在同一个仓库里推送，差的是规矩。
- **每次交活多一两分钟检查**。
- **比赛仓库要公开**：GitHub 对公开仓库免费提供主线保护和自动检查。
- **考虑过的另外两种做法**：
  - 都直接推主线：现在的做法，快，但会打架。
  - 每人一条长期分支，最后再合：过程不打架，结果就是两个游戏。
- **比赛规则会卡住底座**：上一场 VibeHacks #06 的[规则](https://github.com/historycrew5423-art/3d-/blob/main/docs/01-比赛规则要点.md)写明，第一个提交必须在开赛之后；之前只能构思、准备工具、建空仓库，不能先写代码，也不能拿旧项目换皮。照这种规则：
  - 经验卡、提示词、命令和检查属于“准备工具”，按字面可以带。提交时如实写明用了这套工具。
  - 底座是提前写好的游戏代码，多半不能直接带。能带的是它的规格和提示词，开赛后让 agent 照着现场重做，再用同一套自动检查验收。
  - 做好的模型和声音算不算“提前做的”，还有其他拿不准的，先问主办方。
  - 所以每场开赛前先对一次规则，“开赛”命令按结果决定带哪些。底座排在最后做，也是这个原因。
  - 那份规则还要求提交记录能看出整个制作过程。小步交活、每次提交写明是谁和哪个 agent，正好满足这一条。
- **规矩太重没人守**：每条规矩都落成一条命令或一页清单，比赛中不需要记任何东西。
- **自动检查的边界**：管得了“对不对”，管不了“好不好看”和“卡不卡”。沙盒里的画面是模拟出来的，帧数和真机差很多，这两样仍然要在真手机上看。
- **工作量**：入库命令、试衣间、底座里的镜头界面声音零件，是整套东西里最花工夫的一块。
- **还没实测的**：WorkBuddy 的发布能不能自动化；WorkBuddy 自动读哪个入口文件。

   - [`feat/survivor-heroes`](https://github.com/historycrew5423-art/hackathon-3d-game/tree/feat/survivor-heroes)：1 个提交，和 `feat/naiwa-meme` 的第一个提交是同一个。

7. **手册仓库的名字**：默认 `hackathon-kit`。
8. **要不要参考队长 Mac 上已经装的几个现成 skill**：看名字和 3D 网页游戏的开局、模型接入、离线打包有关。建的时候参考能省事。它们来自别处，到现在没有打开过。
